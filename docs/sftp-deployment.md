# SFTP deployment

## Install and use

1. Build with `npm run build:packages`, or only this package with `node --input-type=module -e "import('./packages/tools/build.mjs').then(m => m.buildToolsPackages({ ids: ['deployment'] }))"`. In **Packages → Install directory…**, select `dist/packages/deployment`, then enable **SFTP Deployment**. Generated release catalogs include the package; an older published catalog may not list it yet.
2. Open **Deployment** in the status bar, **Settings → Configure deployment…**, or action search. Choose **New server…**. Enter connection details and a remote root (`.` means the authenticated user's home). Passwords and encrypted-key passphrases can stay in the worker session or be saved in macOS Keychain. For an agent, the IDE process must inherit `SSH_AUTH_SOCK`.
3. Use **Review server key**, compare the displayed SHA-256 fingerprint with a trusted source, and explicitly trust it. **Test connection** checks authentication and root access. Configure mappings, exclusions and options, then **Save server**. No files are sent by saving settings.
4. Choose a local file/folder and **Preview upload**, **Current file**, or **All mapped files**. The Project context menu's **Upload with SFTP…** also opens this selection. Review every destination, compare text as needed, select files, then click **Upload**. Conflicts require explicit selection; unchanged and blocked files cannot be selected. Local unsaved editor buffers are not sent.
5. **Browse remote files** and folder buttons navigate within the configured root; **Up** moves to the parent. **Transfers** shows progress, per-file outcomes and cancellation. Closing the dialog keeps a transfer running. Disabling/restarting the package, changing workspace or a full workspace refresh stops it. The latest transfer is retained across worker restarts; transfers never resume automatically.
6. To opt in to automatic uploads, choose a default server and select **After saving in Zwip, to the default server**. Only successfully acknowledged IDE saves are queued. A changed disk source or an unfamiliar/changed remote version needs manual review. Renames upload the new file on save; the old remote filename remains.

Limits: 50 servers, 30 mappings per server, 5000 files and 1 GiB per preview, 1 MiB per text comparison, four retained previews expiring after 15 minutes, and the latest transfer log. Remote file reads have a 60-second deadline; SSH connection and SFTP operation timeouts are bounded. New files default to 644 and new directories to 755 unless overridden. Metadata is applied after publication; interrupted finalization can leave the uploaded file private (600), and Transfers reports that warning.

## Research and scope

This package follows IntelliJ IDEA's upload workflow, rather than copying its implementation or branding. The relevant official references are [server connections](https://www.jetbrains.com/help/idea/deployment-connection-tab.html), [path mappings](https://www.jetbrains.com/help/idea/deployment-mappings-tab.html), [excluded paths](https://www.jetbrains.com/help/idea/deployment-excluded-paths-tab.html), [deployment options](https://www.jetbrains.com/help/idea/settings-deployment-options.html), [uploads](https://www.jetbrains.com/help/idea/uploading-and-downloading-files.html), and [remote comparison](https://www.jetbrains.com/help/idea/comparing-deployed-files-and-folders-with-their-local-versions.html). The transport uses the pinned [ssh2 client](https://github.com/mscdex/ssh2/tree/v1.17.0) and its documented [SFTP operations](https://github.com/mscdex/ssh2/blob/v1.17.0/SFTP.md).

The optional **SFTP Deployment** package is independent of language packages. It supports multiple project-scoped servers, a default server, password/private-key/SSH-agent authentication, explicit host-key trust, connection testing, multiple local/remote mappings, exclusions, remote browsing, local/remote text comparison, reviewed manual uploads, and opt-in upload after successful IDE disk saves. Automatic uploads never observe external disk changes, Git checkouts, unsaved buffers or local deletions. No FTP, FTPS, WebDAV, jump hosts, SSH configuration import, rsync, server groups, remote deletion, remote editing, downloads or two-way synchronization are included. IDEA's broader deployment suite includes capabilities beyond this upload-focused package.

## UI and settings plan

- **Entry points:** Deployment in the workspace status bar; action search commands for deployment and uploading the current file; a Project context action for uploading a file or folder; a Deployment link in Settings. Missing/disabled-package states link to Packages and never silently install or enable anything.
- **Deployment window:** a wide existing-style dialog with a saved-server selector, default-server indicator, Configure and Refresh controls. Upload current file, a workspace-relative file/folder selection, or all mapped files. Remote browser shows folders first, the current path/up navigation, file sizes and modified dates; links and unsupported files are visibly unavailable. Transfers remain active when this window closes.
- **Server editor:** separate Connection, Mappings, Exclusions and Options sections. Connection fields: name, host, port (22), username, authentication method, private-key path with file picker, credential input and Save in Keychain, remote root, fingerprint review and Test connection. Probe the server key without authenticating; show its SHA-256 fingerprint and require explicit trust. Changing host/port invalidates the draft trust. Changed keys fail closed. Save never connects or uploads.
- **Mappings:** editable local workspace-relative directory and deployment path relative to the remote root, with Add/Remove controls. A nested local mapping takes precedence over its parent. Reject traversal, duplicate local mappings and destinations where two selected files collide.
- **Exclusions:** separate local and remote subtree paths; recursive filename patterns separated by semicolons, supporting `*` and `?`. Initial patterns exclude VCS/editor state, dependency/build directories and common credential files. The chosen private key is always excluded. No symlinks are followed.
- **Options:** default server; automatic upload Never/After saving in Zwip; preserve timestamps; optional new-file/new-directory octal permissions. Uploads always stage to unique temporary files. Existing file permissions are retained unless an override was explicitly configured. No setting implies remote deletion.
- **Preview:** selected server/root and an explicit source-to-target list with size, create/replace/unchanged/conflict/blocked status and reason. Checkboxes select eligible files. An upload button confirms the exact reviewed selection; exclusions and blocked paths cannot be overridden here. Text comparison is read-only and bounded. Dirty buffers are not implicitly saved by deployment; preview reads saved disk content and says so.
- **Transfers:** progress bytes, current file, completed/failed/cancelled counts and a bounded per-file log. Cancel interrupts the active transfer and stops pending files. Failures preserve successful results, do not claim complete success, and are never silently retried. No credentials appear in logs or errors. Automatic-upload conflicts instruct the user to review a manual preview.

## Architecture and storage plan

All SSH, SFTP, mappings, deployment settings, snapshots and transfer logic live in the optional Node worker. The Rust foundation gains only a generic package/workspace-scoped credential contract backed by the existing macOS Keychain dependency. The frontend cannot read saved secrets; the host injects a selected credential directly into a package request. A credential reference is bound to the requesting package and canonical workspace. Database credentials remain separate.

Settings and successful-deployment hashes are stored in the package cache, under a hash of the canonical workspace, outside project source control. Settings use explicit revisions and atomic replacement; stale editor saves fail rather than overwriting newer settings. Credentials never enter those files. Plans are opaque worker-owned tickets tied to settings revision, server identity, canonical remote root, local content hashes and remote content hashes. Bound retained plans/jobs and log history. Changing configuration invalidates pending plans; one transfer job runs per workspace worker. The host already owns worker shutdown when disabled, restarted, switching workspace or closing a window.

Automatic upload listens only to successful `document.save` acknowledgements. A small workspace preference indicates whether checking the optional worker is necessary; it contains only server/credential references, never secret material. Changes to package availability or deployment configuration refresh this listener. Saved paths, content hashes, revisions and generations are coalesced, scoped to their workspace, and uploaded serially. Disk bytes must match the acknowledged save. A stale callback from another workspace cannot upload through the new workspace's worker.

## Transfer invariants and failure handling

1. Resolve the local workspace and configured remote root. Validate every selected path, mapping and exclusion before remote writes. Reject observed local symlinks, nonregular files and remote symlinks at every path component. Creating directories is an upload action, not a preview side effect. SFTP's path-based operations cannot enforce a strict sandbox against concurrent namespace changes or a dishonest server: use a server-side jailed account for that boundary. These checks do not claim to defeat another writer swapping an ancestor after validation.
2. Preview hashes saved local content and existing remote content. Missing files are creates; matching content is unchanged. A remote file differing from the last successfully deployed version is a conflict for automatic upload. Manual preview can explicitly select a replacement. Permission/connection/hash failures are blocked or reported as errors, never treated as absent files.
3. At upload time, validate the plan revision and server/root, snapshot each selected local file into a private temporary directory (700) and file (600), and verify its hash still matches the preview. Changed source files require a new preview. Hashes read from open file handles and byte counts guard concurrent local writes.
4. Create mapped remote directories under the canonical root, checking existing components and symlinks. Write each snapshot to an exclusively created temporary sibling with an explicit 600 initial mode, verified before streaming. Keep it private through the final destination hash check and durable publication journal. A changed destination fails that file instead of overwriting it. Check cancellation immediately before issuing rename.
5. Publish existing-file replacements using the OpenSSH POSIX rename extension. If the server lacks atomic replacement, fail without deleting the original as a fallback. New destinations can use standard SFTP rename. Apply requested timestamps/permissions through the still-open uploaded file handle after acknowledged publication, so a concurrent replacement is not chmodded by path; metadata failures are reported as a partial result and can leave a private uploaded file. Record content success only after publication. Attempt temporary-file cleanup after failed/cancelled transfers.
6. SFTP has no portable compare-and-swap: a different writer can change a destination between the final check and rename. Abrupt disconnects/process termination can leave private temporary siblings. If rename committed but its acknowledgement was lost, the destination may already contain the new bytes: Transfers reports an unknown outcome requiring comparison. A pre-rename journal preserves that uncertainty across restart. Settings remain; transfers are never automatically resumed or retried. Private snapshot files may remain in the package cache after abrupt process termination.

## Implementation and verification sequence

1. Define shared contracts and pure path/mapping/exclusion validation, then prove traversal, overlapping mappings and collision behavior with focused tests.
2. Add pinned SSH dependencies without running dependency install scripts. Implement pinned-key connection/probe, bounded operations, remote browsing and a real local SFTP fixture. Test correct/incorrect host keys and password/key authentication.
3. Implement revisioned settings, preview/snapshot/upload/cancel and persistent baselines. Exercise real SFTP creates, atomic replacements, changed-source/changed-target rejection, symlink escape prevention, exclusions, permissions, timestamps and partial failure/cancellation.
4. Add the generic credential bridge and package build/catalog metadata, including runtime notices/checksums. Test credential scope without reading real user secrets and exercise the built worker through the IDE backend.
5. Build the server editor, deployment window, preview/comparison and job monitor using existing dialog/field/button styles. Test package gating, form validation, fingerprint acceptance, stale responses, save failures, upload selection and failure states. Add IDE save notifications and opt-in automatic upload tests.
6. Update the guide to the final delivered behavior and add a fresh update-history entry. Run the full frontend suite, relevant Rust tests, project checks and production web/package builds; verify the UI and upload behavior in a real browser against a disposable local SFTP server. Stage new project source files; keep generated packages and temporary fixtures unstaged.
