# Native IDE benchmark method

This protocol measures the production desktop application and its attributable helper processes. It does not turn service-only measurements into desktop results. No relative memory or CPU target has been selected; report measured values and uncertainty. Correct navigation, complete workspace coverage and responsive editing remain acceptance gates.

## Sampler

Run `node scripts/bench-native.mjs --help`. The sampler only attaches to an existing PID. It never launches or terminates an IDE, modifies a workspace, invokes Git, or changes IDE settings. It compiles the small diagnostic `bench-native-probe.c` with the installed macOS SDK into a temporary directory, removes it on exit, and writes the requested JSON report. Node and Xcode Command Line Tools are prerequisites. A sandbox may require process-inspection permission; the tool does not request root, disable system protections, or substitute zeros when access fails.

Example for an already running production app with no terminal, test, debug, build or development-server jobs:

```sh
node scripts/bench-native.mjs --pid 12345 --label zwip-production --phase ready-idle --no-tasks --duration 60 --interval-ms 250 --repeat 3 --gap-ms 5000 --worker-prefix '/absolute/package/install/directory' --metadata artifacts/native-workload.json --out artifacts/zwip-ready-idle.json
```

Use the actual PID and paths. For a workload containing user tasks, replace `--no-tasks` with one `--task-pid PID` per task root. Task descendants stay in the separate task group. `--worker-pid` can label a detached provider. `--helper-pid` can include a helper whose ownership was independently verified; this is recorded as an operator assertion, not automatic proof. Explicit PIDs are pinned to their initial process start time. New descendants and helpers are discovered at every sample; remembered identities retain their attribution if reparented. A recycled PID is a different process.

The report records repeated sample windows, per-process counters, attribution evidence, inaccessible counters, ambiguous WebKit helpers, actual intervals, sampler duration, OS/CPU/RAM, power and thermal diagnostics, role assertions and optional workload metadata. The optional metadata JSON should include build/commit, package/plugin versions, workspace revision and source hash manifest, SDKs, dependency cache state, workload actions and their outcome, indexing readiness times, cache mode, display scale and active IDE settings. Do not put credentials or HTTP/SQL contents in the metadata.

Run `node --test scripts/bench-native.test.mjs` to verify the attribution and accounting cases. These tests cover launchd-parented WebKit, unrelated applications, shared outer launchers, explicit task trees, detached processes, PID reuse, CPU interval accounting and unavailable counters. They are measurement-tool tests, not product performance results.

## Process and metric definitions

- The application root, descendants and processes reporting an attributable responsible PID form the observed application group. WebKit WebContent, GPU and Networking services often have `ppid=1`; ancestry alone omits them. The sampler optionally resolves macOS's private `responsibility_get_pid_responsible_for_pid` diagnostic symbol. It never assigns every WebKit process by executable name, nearby launch time, or a shared outer terminal/Codex PID. Unproven ownership is listed separately and excluded. If an app inherits its launcher's responsibility, use a normal production application launch and revalidate ownership, or independently verify explicit helper PIDs.
- `proc_pid_rusage(RUSAGE_INFO_V4)` supplies `ri_phys_footprint`, `ri_resident_size`, `ri_user_time` and `ri_system_time`. Footprint and RSS are reported as distinct byte measurements. Their process sums are kernel ledger charges and resident mappings, respectively, not a claim about incremental whole-system RAM. Shared pages can be counted in multiple processes; compression can make RSS much smaller than footprint.
- CPU seconds are observed user plus system counter deltas during each window. The raw rusage time counters are Mach absolute ticks; the native probe converts through `mach_timebase_info` with a 128-bit intermediate (the timebase is recorded), rather than assuming nanoseconds. Existing process lifetime CPU is subtracted. First observations of processes born during the window include their observed CPU since birth. CPU percent uses one logical core as 100%, so multithreaded work can exceed 100%. It is not divided by machine core count.
- A process born and exited between samples is absent; work after a process's last observation is also missed. Observed CPU is consequently a lower bound, and periodic memory sampling can miss peaks. Repeat at 50–100 ms for a short cross-check if process churn matters, while measuring sampler overhead. Do not silently compare runs with different intervals.
- Missing selected counters produce incomplete coverage and null memory aggregates for that sample. Unknown WebKit attribution blocks an unqualified whole-app resource claim. Unmarked user task processes may remain in IDE totals; task separation must be verified before comparison. Systemwide services, GPU-wide allocations and filesystem cache changes are not completely apportioned by this sampler.
- Repeated windows in one running session measure within-session variation. Independent startup trials require separately launched app sessions, new root PIDs and separate reports. The sampler does not establish first-frame or interactive startup latency; capture those events with the native UI workload separately.

The metric definitions are grounded in Apple's [task rusage implementation](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/bsd_kern.c), [libproc declarations](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.h), [resource counter definitions](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/resource.h) and [process identity metadata](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h). The optional responsibility symbol is a private API also used in [Chromium's macOS process implementation](https://chromium.googlesource.com/chromium/src/+/refs/tags/134.0.6998.28/base/process/process_info_mac.mm); its availability is tested and reported at runtime. It is confined to this diagnostic executable and is not part of the shipped IDE.

## Equivalent workload

1. Create two disposable copies of the same pinned workspace revision, including matching uncommitted source content when relevant. Record hashes of tracked source and configuration before and after. Do not open the original `goserving` in a benchmark that may create `.idea` files or rewrite project configuration. Both copies need equivalent installed frontend dependencies, Go modules, build tags, environment, exclusions and SDK versions. Record generated files separately.
2. Use the production release application bundle, without Vite, devtools, test injection, WebDriver or debug instrumentation. Record its commit and package checksums. For IntelliJ, record the exact edition, build, JBR, heap flags, enabled plugins, indexing/exclusions and project roots. First compare the user's actual plugin profile as such. A reduced equivalent-functionality IntelliJ profile is a separate experiment in a disposable settings directory and must be explicitly identified; do not silently disable work to improve either result.
3. Verify semantic readiness for every included context: all 33 Go modules and both frontend projects in the reference workspace, or an explicitly identical smaller scope in both apps. Indexing indicators alone are insufficient. Run the same source-adjudicated queries and compare exact targets, implementations and explicit hierarchy edges. Separate unresolved dependencies, unsupported SDK syntax and partial results; these fail the equivalence gate rather than count as faster queries. The existing 12 Go and 12 Web source oracles can seed this comparison, but are not captured IntelliJ results.
4. Measure distinct phases: launch-to-interactive; cold project analysis with dependencies already present; readiness-to-idle settling; 60-second ready idle; a fixed navigation sequence; typing/completion with the same open tabs and unsaved buffers; a reviewed Git status/diff/push-preview sequence against a disposable local remote; and, separately, an identical test/debug/build task. Never perform a real push or fetch that changes the user's remote state. Keep task cost separate from app/provider cost.
5. Warm navigation: use a fixed seeded order, one unreported warm-up per query, then at least 30 measured requests for each operation. Record request-to-visible-result latency, exact target correctness, state/coverage and UI input latency independently. Report p50/p95 and raw samples; a p99 from 30 observations is effectively a maximum and is not stable evidence. For typing, record event-to-next-paint through the real WKWebView and include dropped or deferred input, selection/IME behavior and cancellation.
6. Cold analysis: use fresh disposable IDE index/cache directories for each trial without changing SDK/dependency caches. Call this **cold IDE cache**, not cold OS cache. Do not purge the machine's filesystem cache or use administrative cache-clearing commands. Warm-cache trials reuse the stated cache state. Run at least five independent app trials, alternate A/B then B/A order, avoid simultaneous measured IDEs, keep AC/low-power/display conditions fixed and record background load. Run-to-run variation and medians matter more than one favorable sample.
7. A ready-idle window starts only after all contexts are ready, the fixed correctness probes pass, and task activity has stopped. Record the settling duration instead of subtracting it. Indexing or garbage collection continuing during the window is part of the measured behavior and must be labeled. Sample resources throughout the same interval as native interaction measurements.
8. Compare absolute MiB, observed CPU seconds, sampled peaks and latency distributions, with individual trials and coverage exclusions. A speed or resource claim requires equivalent completed work, correct results, native interaction evidence and a difference larger than observed run-to-run noise. No comparison is qualified merely because `bench-native.mjs` completed; reports deliberately set `qualifiedComparison: false` pending this external review.

## Disposable workspace and IntelliJ profile

`scripts/bench-native-prepare.py` copies the Git-listed tracked and nonignored untracked files from the reference workspace into two independent directories. It excludes dependency/build caches, Git metadata and nested repositories/worktrees, records every included source file's SHA-256, verifies both copies and rechecks the original after preparation. Writable source files are copied, never hard-linked. The two frontend dependency trees are copied from a dependency-complete workspace only after their package manifests and lockfiles match. Dependency symlinks must stay inside each copy. A source symlink requires explicit review rather than silently following it.

```sh
python3 scripts/bench-native-prepare.py --workspace /Users/grejo.j/IdeaProjects/goserving --dependencies /absolute/dependency-complete-copy --intellij-config '/Users/grejo.j/Library/Application Support/JetBrains/IntelliJIdea2022.3' --out artifacts/native-benchmark
```

The generated `preparation.json` records the actual paths, source revision, full file hash manifest, included module count, exclusions and verification result. The prepared reference snapshot contains **9,432 source files and 33 Go modules**, plus matching installed dependencies for Atlas and Quizstudio. The original hashes were unchanged. Use a new stable `--out` directory for sustained work: copies preserve original modification times, and temporary-directory cleanup can remove older files. Recheck hashes immediately before each measured workload. The separate source copies have no `.git`; initialize independent disposable repositories before Git workloads.

The optional IntelliJ profile retains the installed plugins, disabled-plugin list, heap override and selected editor/analysis preferences. It omits account tokens, licenses, SSL data, database connections, consoles, recent projects and session history. `reopenLastProject` is disabled so startup cannot reopen the original workspace. This is an isolated profile with selected existing settings, not a byte-identical copy of all personal state. License activation may require the user; do not copy authentication material to bypass it.

After native-test activity has stopped and launch is authorized, the prepared properties file can select the isolated profile without modifying the application bundle or normal settings:

```sh
IDEA_PROPERTIES='/absolute/prepared/intellij-profile/idea.properties' '/Applications/IntelliJ IDEA.app/Contents/MacOS/idea' '/absolute/prepared/intellij-workspace'
```

Verify the effective config/system/plugins/log paths, heap flags and loaded plugins in that running instance before sampling. `idea.config.path`, `idea.system.path`, `idea.plugins.path` and `idea.log.path` are set to distinct prepared directories. JetBrains documents these [directory properties](https://www.jetbrains.com/help/idea/directories-used-by-the-ide-to-store-settings-caches-plugins-and-logs.html), the [`IDEA_PROPERTIES` override](https://www.jetbrains.com/help/idea/tuning-the-ide.html) and the [macOS command-line launcher](https://www.jetbrains.com/help/idea/working-with-the-ide-features-from-command-line.html). The installed 2022.3 bundle's `idea.properties` independently lists the same four directory settings. Preparation does not launch either IDE.

## Initial indexed-idle observation, 2026-10-13

Three 30-second windows of the same isolated IntelliJ session are saved locally in `artifacts/intellij-indexed-idle.json`. Attributable process counters were available in every sample; no ambiguous WebKit ownership was reported. Median summed physical footprint was 2,982.4 / 2,982.5 / 2,982.7 MiB; median summed RSS was 279.6 / 341.5 / 348.9 MiB. Mean CPU was 1.55 / 2.39 / 1.67 percent of one logical core. Footprint and RSS measure different things; their large difference must not be interpreted as a memory saving.

This is **indexed idle, not qualified semantic-ready idle or a Zwip comparison**. The 24 exact navigation queries had not been checked when sampled. The M1 Pro host has 16 GiB RAM and 10 logical CPUs, was on battery at 78 percent, and reported a one-minute load average of 6.81 before sampling. The existing 1,000 MiB Java heap had produced low-memory warnings. No native UI actions or application tasks ran during these windows. Repeated windows share one application/cache session; they are not independent startup trials. These conditions prevent treating the observations as release acceptance or a controlled performance advantage.

On the morning of 2026-10-13, 9,384 older source files were found missing from each temporary copy; the 48 surviving files had recent modification times. All original source hashes still matched. Directory timestamps and the age split are consistent with temporary-file cleanup, but the deleting process was not independently established. Later IntelliJ query attempts were stopped, the owned isolated process was closed, and those damaged copies were retained as evidence. The earlier continuous idle windows remain observations of their recorded session only; they cannot establish a current equivalent-workspace comparison. Fresh copies are prepared under the ignored project `artifacts/` directory and require a new integrity/readiness check.

## Prerequisites still required for comparable measurements

- A finalized production Zwip build and recorded installed package versions/checksums.
- A running production PID with verified ownership of its WebContent/GPU/Networking helpers; idle resource sampling alone is not UI qualification.
- A disposable dependency-complete workspace copy for both IDEs, matching context/exclusion/SDK setup, and a compatible IntelliJ runtime validated against the same exact-target queries.
- Native automation or a reproducible operator script for the same actions, with timestamps and readiness evidence. Resource windows must align with those actions.
- Separate cold-cache and warm-cache trials under recorded power/background-load conditions, with no real source or remote mutations.

The repository's existing `scripts/bench-workspace.mjs` remains a service benchmark. Its results are useful for server/query diagnosis but exclude WKWebView and cannot substitute for this native comparison.
